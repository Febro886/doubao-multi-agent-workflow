# 可行性测试

本文档教你怎么主动验证这个 3-Agent 协作 Workflow 是否可行。

------

## 一、测试目标

| 验证点          | 要求                | 怎么算「可行」                               |
| --------------- | ------------------- | -------------------------------------------- |
| 流程完整性      | 端到端跑通          | 3 个 Agent 依次执行、三份产出依次打印在终端  |
| Agent 协作/互通 | 消息传递 + 状态共享 | 下游 Agent 产出的内容里包含上游需求/设计产物 |
| 可运行性        | MVP 可运行即可      | 不装任何 Key、不联网也能跑通（mock 模式）    |
| 鲁棒性          | ——                  | 空需求、英文、特殊字符都不报错               |

------

## 二、三种测试方法（任选，推荐先用 A）

### 方法 A：自动化测试（最省事，一键验证）[推荐]

```
cd doubao-multi-agent-workflow
python test_workflow.py
```

脚本会跑 12 个检查项，全部打印 `[PASS]` 且最后显示
`总计: 12/12 通过` 和 `结论: 项目可行性验证通过 (可行)`，即可判定可行。
（若某项为 `[FAIL]`，脚本会给出原因，按提示修改即可。）

覆盖用例：

- 共享状态写入/读取、下游读取上游产物、通信日志完整
- 需求/设计/编码三个 Agent 产出质量 + 信息互通
- 端到端跑通 5 段产品需求描述：中文、中文业务、英文、空、特殊字符

### 方法 B：手动功能测试（用测试数据，直观看产出）

测试数据见同目录 `sample_requirements.txt`（直接复制粘贴，也可抄下表）。
手动运行时你自己输入一段产品需求描述，需求 Agent 会把它标准化成需求文档。
注：当前版本不落盘保存，三份产出直接打印在终端。

| 编号 | 输入（产品需求描述）                                         | 类型     | 预期产出                                                     |
| ---- | ------------------------------------------------------------ | -------- | ------------------------------------------------------------ |
| T1   | `我想做一个帮助团队管理任务的待办事项系统，支持创建任务、设置截止日期、标记完成，并支持多人协作。` | 中文默认 | 终端依次打印需求/设计/代码三份产出                           |
| T2   | `用户想要一个在线订餐平台，支持浏览菜单、下单、查看订单。`   | 中文业务 | 设计/编码产出包含「标准化软件需求文档/技术设计文档」字样（互通证据） |
| T3   | `Build a student grade management system with course and score tracking.` | 英文     | 三份产出正常打印，无乱码                                     |
| T4   | （直接回车，不输入）                                         | 空需求   | 自动使用默认需求示例，不报错                                 |
| T5   | `Test #1 & 'quote' project description.`                     | 特殊字符 | 流程不崩溃，正常产出                                         |

操作步骤：

```
python main.py
```

根据提示依次输入 T1~T5 的需求描述，每次回车后观察：

- 终端是否依次打印需求、设计、代码三份产出，且内容与该需求描述相关
- 终端是否打印 `Workflow 完成：3 个 Agent 已通过共享状态完成信息互通。`

判定可行：每次都打印完成提示，且三份产出齐全、内容与需求相关。

### 方法 C：真实引擎测试（进阶，验证「真 Agent」）

三个 Agent 默认接入火山方舟豆包大模型（Doubao-Seed-2.1-pro）。验证真实生成：

1. 把 `.env.example` 复制为 `.env`，填入火山方舟的 API Key（`ARK_API_KEY=` 后面填 Key 本身；`.env` 已加入 `.gitignore`，切勿提交）。
2. 先跑连通性自检：

```
python test_ark.py
```

打印出豆包的真实回复，即表示 Key 与模型配置无误。

1. 再运行主流程：

```
python main.py
```

环境检测会显示三个 Agent「已设置 -> 将使用真实模型 doubao-seed-2-1-pro-260915」；输入一段需求后，观察产出是否为真实模型生成的内容（不再是模板）。
注意：pro 为深度思考型模型，整轮流程约 5–10 分钟，请耐心等待，不要中途中断。

## 三、如何判断「可行性」成立（验收清单）

- 方法 A 脚本输出 `12/12 通过`
- 方法 B 中 T1~T5 都能跑完，终端三份产出齐全
- T2 的设计/编码产出中能看到「标准化软件需求文档」「技术设计文档」字样（证明上游→下游信息互通）
- 空需求（T4）不报错

满足以上即证明：该项目满足「至少 2 个 Agent 协作、Agent 间通信、顺序流程控制、可运行」的全部设计要求，可行性成立。

## 四、常见问题排查

| 现象                   | 原因                         | 解决                                                         |
| ---------------------- | ---------------------------- | ------------------------------------------------------------ |
| 终端输入中文后显示乱码 | 个别旧终端编码问题           | 用回车默认需求或英文需求；文件本身以 UTF-8 保存              |
| 启用真实引擎报错       | 未配置 Key / 断网 / 请求超时 | 检查 `.env` 中 `ARK_API_KEY` 是否填对；确认网络可达；长文档生成较慢，超时已设为 600 秒，不要中途中断 |
| `No module named ...`  | 依赖未装                     | `pip install -r requirements.txt`                            |
